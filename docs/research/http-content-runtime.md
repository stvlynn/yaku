# Ordinary HTTP content runtime

An installed Chrome extension's content-script world must be tested separately from the page world and from extension pages. On a normal nonlocalhost HTTP origin, the isolated content world can inherit an insecure context even though its execution-context origin identifies the extension.

## Confirmed observation

`scripts/experiments/http-content-crypto.mjs` loaded the actual unpacked extension into a fresh independent Chrome profile, compared its executed background source with the built file, and opened a unique `http://ordinary-http-fixture.test` page. CDP enumerated the actual `Yaku` isolated context; `chrome.runtime.id` matched the installed extension ID. It inspected globals without replacing APIs or starting model inference.

| World                               | isSecureContext | crypto.randomUUID | crypto.getRandomValues |
| ----------------------------------- | --------------- | ----------------- | ---------------------- |
| Ordinary HTTP page                  | false           | undefined         | function               |
| Playwright utility world            | false           | undefined         | function               |
| Installed Yaku content-script world | false           | undefined         | function               |

The content context's metadata reported an extension origin while `location.origin` remained the HTTP page. This is actual installed-content evidence, not an inference from ordinary-page behavior. The tested background SHA matched the fixed checkpoint, and the result JSON has `completed:true`. Old destroyed pre-navigation contexts are also recorded as unavailable CDP contexts; they were not mistaken for the actual content world. Evidence is `.workspace/qa/http-content-crypto.json`.

MDN documents [`randomUUID`](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/randomUUID) as requiring a secure context, whereas [`getRandomValues`](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/getRandomValues) is available in insecure contexts. The observed distinction explains why HTTP-reachable page/context/native-caption request creation could fail before inference while extension-origin workspace operations worked.

## Narrow fix and verification boundary

The three HTTP-reachable feature slices use `shared/request-id`'s `createRequestId()`, which encodes 16 cryptographically generated bytes as opaque hex. There was no UUID-format requirement in the request contract. There is no Math.random or silent unavailable-crypto fallback. Extension-origin-only operations retain their existing built-in UUID use. The selection dialog independently uses a fixed title ID scoped by its own ShadowRoot.

The post-build `scripts/experiments/http-request-paths.mjs` completed on the actual installed content world of ordinary HTTP. It invoked normal registered selection, input and page commands and added a real native VTTCue. Each path emitted a request; six observed IDs were distinct 32-character lowercase hex strings, and no page exceptions occurred. The content context still had `isSecureContext:false`, unavailable `randomUUID` and working `getRandomValues`; the executed background matched the built source. `.workspace/qa/http-request-paths.json` records `completed:true`.

That driver intercepts only the test context's outgoing translation messages and supplies controlled echo replies to isolate request creation. It exercises production content actions and ID generation but does not claim model inference, semantic translation, native operating-system menu selection, or arbitrary HTTP sites. The separate `native-tracks-real-model.mjs` then passed actual installed native-track acquisition, source-hint selection, Chinese HY-MT2 inference and bilingual VTT export on ordinary HTTP, with `randomUUID` still unavailable and valid CSPRNG IDs observed. Its completed result is recorded in [native caption verification](native-caption-tracks.md). Page/context checks remain controlled request-start evidence rather than an additional HTTP semantic corpus; HTTPS/model acceptance alone is not used as proof of HTTP compatibility.

No protocol/permission weakening, remote executable script, HTTPS upgrade or arbitrary network proxy is used to bypass this issue. The compatible CSPRNG API fixes the observed cause directly. Model download, source-language policy and provider-specific subtitle acquisition are separate workflows.
